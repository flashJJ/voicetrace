# 03 · 好想法调研方案

> 目标：在 8 天内找到一个“有人痛、有人付、没人做好、你做得出来、评委看得懂”的想法。  
> 方法：先发散，再评分，再做 48 小时验证，最后冻结范围。  
> 结论：通用评分最高的是 **交付验收官**，但你已根据“暂无 B 端用户资源、优先故事/曝光”的实际约束，选定 **非遗/方言互动叙事（声迹 · 方言故事书）**。交付验收官、账单差异排查保留为备选。

## 1. 好想法的 7 个标准

| 标准 | 要问的问题 | 不合格的信号 |
|---|---|---|
| 痛点强度 | 用户会不会为这件事焦虑/损失钱/丢面子？ | “有了更好，没有也行” |
| 频率/刚性 | 多久发生一次？是必须做还是可选做？ | 一辈子一次，且不急 |
| 付费意愿 | 谁付钱？预算从哪来？现在花多少钱？ | 用户说“好玩，但不会付费” |
| 竞争空白 | 现有方案哪里不好？我们能不能 10 倍好？ | 竞品免费且够用 |
| 8 天可交付 | 能不能做出完整闭环，而不是 Demo？ | 需要硬件、供应链、长期数据 |
| 演示冲击 | 3 分钟内能不能让人“哇”？ | 需要 20 分钟解释背景 |
| 评委契合 | 能不能命中一个专项奖？ | 说不清属于哪个赛道 |

## 2. 20 个提问（想法生成器）

### 从“重复劳动”找

1. 哪些工作每周重复 3 次以上，而且结果要给人看？
2. 哪些流程需要“复制粘贴 + 改格式 + 发出去”？
3. 哪些报告/清单/台账是人工拼出来的？
4. 哪些审批/验收/对账需要跨多个文件核对？

### 从“高金额、不可逆决策”找

5. 哪些决策金额大、信息不对称、后果不可逆？（装修、婚礼、留学、手术、买房、投保）
6. 哪些合同/报价/账单里，普通人看不出问题？
7. 哪些“签字/付款/验收”节点最容易扯皮？
8. 哪些服务在线下收费高、体验差、信息不透明？

### 从“新能力”找

9. 哪些新模型能力（长上下文、视觉、语音、工具调用）让过去不可能的产品变得可能？
10. 哪些平台刚开放 API/政策（微信、支付宝、飞书、鸿蒙、抖音）？
11. 哪些数据以前无法结构化，现在可以（图纸、视频、录音、单据）？
12. 哪些“专业判断”可以被拆成规则 + AI 解释？

### 从“被忽略的人群”找

13. 哪些人群被通用工具忽略？（老人、听障、蓝领、小微商家、自由职业者、县域用户）
14. 哪些人需要“陪跑”，而不是一个工具？
15. 哪些人面对专业术语时完全无助？

### 从“抱怨/差评”找

16. 哪些社区抱怨最多？（V2EX、知乎、小红书、GitHub issues、App Store 一星）
17. 哪些“避坑攻略”点赞很高，但没人做成工具？
18. 哪些服务需要“人工审核”，但审核标准其实可以结构化？

### 从“生成过剩、验证不足”找

19. 哪些领域“生成”已经过剩，但“审核/验证/追责”严重不足？
20. 哪些作品“看起来完成了”，但没人能证明它真的完成？

> 第 19、20 条是本次比赛的关键洞察：AI 让生成变得便宜，**验证、证据、责任**反而更值钱。

## 4. Top 3 详细分析

### 4.1 方案 A：交付验收官（通用评分首选，现为备选）

**一句话**：把合同/SOW 变成可执行的验收清单，自动跑一遍，生成客户敢签、你能收尾款的验收报告。

**目标用户**：

- 软件外包公司/工作室的项目经理、交付负责人；
- 自由职业开发者、独立开发者；
- 甲方（企业/政府/学校）的项目负责人、采购/信息化部门。

**真实痛点**：

- 合同里写的是“功能完整、运行稳定”，验收时却变成“这个按钮颜色不对”；
- 需求文档、原型、代码、部署环境、账号权限散落在不同地方，没人能证明“到底交付了什么”；
- 甲方怕付了钱拿不到东西，乙方怕干完活收不到尾款；
- 验收标准不清晰，导致无限改稿、尾款拖欠、甚至诉讼。

**现有方案**：

| 方案 | 问题 |
|---|---|
| Excel/Word 验收清单 | 手工维护、无证据、容易漏项 |
| 项目管理工具（禅道/ONES/Jira） | 管任务，不管“验收证据” |
| 测试管理工具（TestRail 等） | 管测试用例，不管合同/SOW |
| WPS AI 验收报告 | 生成报告文档，不做实际检查与取证 |
| 通用 AI | 可以写清单，但不能跑检查、不能留证据、不能出报告 |
| 律师/仲裁 | 成本高、周期长，事后补救 |

**产品闭环**：

1. 上传合同/SOW/需求文档（PDF/Word）→ AI 抽取交付物、验收标准、边界、付款节点。
2. 生成验收清单（功能/性能/安全/文档/部署/权限/培训），每项带“检查方法”。
3. 输入体验链接/测试账号/仓库 → 自动检查：页面可打开、关键流程可走、移动端适配、性能、无障碍、安全头、死链。
4. 人工勾选 + 上传证据（截图、日志、录屏），形成证据链。
5. 生成验收报告 PDF：通过/不通过/风险项/整改建议/客户签字页。
6. 可选：生成“遗留问题清单”和“交付说明”，减少扯皮。

**差异化**：

- **从合同开始，到签字结束**：不是通用测试工具，而是“验收”这件事的端到端产品。
- **证据链**：每个结论都有截图/日志/时间戳，可导出、可追溯。
- **中文场景**：中文合同/SOW、微信/支付宝/飞书/企微集成、等保/个人信息保护 checklist。
- **双端**：乙方用来准备交付，甲方用来验收；双方用同一份清单，减少争议。
- **8 天可交付**：先支持“企业官网/管理后台/小程序”三类项目，不追求全行业。

**竞品**：

- MilestoneProof（海外 hackathon 项目）：按 SOW 校验外包交付物，偏代码审查，无中文场景、无完整验收报告。
- WPS AI 验收报告：生成文档，不做实际检查。
- 禅道/ONES/Jira：项目管理，不解决验收证据。
- TestRail/测试平台：测试管理，不解决合同/SOW 对齐。

**MVP 范围（8 天）**：

- 支持 1 种项目类型：企业官网/管理后台（含登录、列表、表单、导出）。
- 支持 1 种输入：上传 PDF/Word SOW + 一个公开体验链接。
- 生成 15-20 项验收清单，覆盖功能、内容、性能、移动端、安全、文档。
- 自动检查 5-8 项：可访问性、关键页面、移动端截图、性能分数、死链、安全头、隐私政策。
- 生成 1 份 PDF 验收报告 + 1 个分享链接。
- 提供 1 个示例项目，评委无需上传即可体验。

**风险**：

| 风险 | 应对 |
|---|---|
| 评委觉得偏 B 端、不够好玩 | 用“尾款纠纷”故事开场；演示一份“差点被坑 3 万”的验收报告 |
| 自动检查覆盖不足 | 明确“AI 检查 + 人工确认”，不承诺全自动 |
| 合同解析不准 | 先支持结构化模板；提供人工修正；标注置信度 |
| 法律责任 | 定位为“辅助工具”，报告注明“不构成法律意见” |
| 真实项目难找 | 用你自己的/朋友的脱敏项目做样本；找 3 个自由职业者试用 |

**评委契合**：行业服务/客户交付产品、商业增长、效率革新奖、商业价值奖。

**一句话故事**：“我接过一个 8 万的外包，尾款拖了 6 个月，只因验收标准没写清楚。后来我用 TRAE 做了交付验收官，让每一次交付都有据可依。”

### 4.2 方案 B：账单差异排查（强备选）

**一句话**：上传两套账单，3 分钟定位每一笔差异的原因和责任人。

**目标用户**：

- 电商商家（微信/支付宝/抖音/拼多多/ERP 对账）；
- SaaS/订阅制公司（支付网关 vs 内部订单）；
- 支付服务商/代运营/财务外包。

**真实痛点**：

- 订单、支付、退款、手续费、结算周期、时区、重复支付，任何一项对不上都要人工翻几十页 Excel；
- 财务只知道“总数对不上”，不知道“哪几笔、为什么、谁负责”；
- 月底对账熬夜，差异原因靠猜。

**现有方案**：

| 方案 | 问题 |
|---|---|
| Excel VLOOKUP | 手工、易错、无法解释差异原因 |
| ERP/财务软件 | 有对账模块，但配置重、不灵活、不解释 |
| 对账 SaaS | 偏大客户、按交易量收费、接入周期长 |
| 通用 AI | 可以解释，但不能稳定匹配、不能出调账建议 |

**产品闭环**：

1. 上传两套 CSV/Excel（渠道账单 vs 内部订单）。
2. 自动识别字段、统一时区/币种/金额口径。
3. 匹配订单号/金额/时间，分类差异：时间差、手续费、退款、重复、漏单、金额不符。
4. 对每类差异给出原因解释 + 证据 + 建议动作（补单/调账/联系渠道）。
5. 导出差异报告 + 调账明细。

**差异化**：

- 不是“又一个对账工具”，而是“差异原因解释器”；
- 支持中文渠道（微信/支付宝/抖音/拼多多）和常见 ERP 导出格式；
- 输出“可给老板/财务看的解释”，而不只是差额数字。

**MVP 范围**：支持 1 个渠道（微信支付）+ 1 种内部订单 CSV；5 类差异；1 份报告。

**风险**：数据敏感、真实账单难拿、竞品多。需要用脱敏样本和“解释能力”做差异化。

**评委契合**：商业增长、效率革新奖、商业价值奖。

### 4.3 方案 C：非遗/方言互动叙事（已选定）

**一句话**：把一段方言、一门手艺，变成可玩、可听、可分享的互动故事。

**目标用户**：离乡年轻人、家庭、地方文化爱好者、学校/社区文化教育者、非遗传承人/文旅机构。

**真实痛点**：

- 老人声音和方言故事没有被保存，等到想记录时可能已经来不及；
- 现有方言产品多是翻译/朗读/识别工具，缺少“可参与、可分享”的情感体验；
- 年轻人听不懂方言，长辈的故事传不下去；
- 文旅/非遗内容同质化，缺少“跟我有关”的入口。

**产品闭环**：

1. 录音/上传一段 1-3 分钟的方言故事（长辈原声优先）。
2. AI 转写 + 普通话翻译 + 方言词注释。
3. 生成 3 幕互动故事，每幕 2-3 个选择；用户可听原声、看字幕、点词注释。
4. 生成“声音故事卡”，可分享。
5. 故事钉在地图上，形成家庭/社区/地方的“声音地图”。

**差异化**：

- 不是“又一个 AI 故事生成器”，而是“真实家庭故事 + 真实原声 + 可互动 + 可分享”；
- 与乡音计划·读侨批（固定历史信件）、瓯小鹿（翻译工具）、瓷都小匠（官方大制作）形成差异；
- 情绪价值强，适合拿“造物故事奖/乐在其中奖”，也容易被官方传播。

**MVP 范围**：1 种方言、3 个种子故事（2 个公有领域 + 1 个真实家庭故事）、3 幕剧情、1 张分享卡、1 张声音地图。

**风险**：素材授权、方言 ASR/TTS 质量、内容制作成本、商业价值弱、同质化。

**评委契合**：游戏娱乐、文化传播、造物故事奖、乐在其中奖。

## 5. 48 小时验证计划

### 5.1 访谈（5 人）

| 对象 | 找谁 | 关键问题 |
|---|---|---|
| 软件外包/自由职业者 | 朋友、前同事、接单群 | 上一次验收扯皮是什么？尾款拖了多久？现在怎么证明交付完成？ |
| 电商商家/财务 | 淘宝/拼多多商家群、代运营 | 上次对账差异多少？怎么找到原因？花了多久？ |
| 文化/内容从业者 | 地方文旅、非遗机构、内容创作者 | 现在怎么记录/传播？最难的是什么？ |

### 5.2 落地页/假门测试

- 用一个页面讲清楚“一句话 + 3 个截图 + 价格”。
- 放“预约体验/加入等待名单”按钮，记录点击和留资。
- 不发朋友圈求人情，去目标用户聚集的社群发。

### 5.3 方向 C 的 48 小时验证（当前）

| 验证 | 怎么做 | 成功信号 |
|---|---|---|
| 录音可行性 | 今天找 1-2 位家人/朋友录 1-3 分钟方言故事，拿授权 | 能拿到 ≥2 段可用音频 |
| 情感反应 | 给 5 个人听 30 秒原声 + 看 1 幕互动，观察反应 | ≥3 人主动说“想录自己家人的声音” |
| 完成率 | 让 10 个人独立玩完 3 幕故事 | ≥7 人完成，平均时长 ≥2 分钟 |
| 分享意愿 | 问“你会把这个故事卡发给谁？” | ≥3 人愿意分享/转发 |
| 付费意愿 | 问“如果帮你把家人的故事做成一本互动书，你愿意付多少？” | ≥2 人愿意付 ≥39 元/本 |
| 差异化 | 给用户看乡音计划/瓯小鹿/猫箱，问“这个和它们有什么不同？” | 用户能说出“这是我家的故事/可以选/可以听原声” |

**如果验证失败**：

- 拿不到音频 → 先用公有领域故事 + TTS 做示例，但仍需 1 段真实录音。
- 用户只觉得“好玩”但不想录 → 强化“家庭记忆/长辈声音”的痛点，或换到“方言童谣给孩子的启蒙”场景。
- 用户觉得和猫箱没区别 → 强化“真实原声 + 家庭故事 + 地图”的差异，减少 AI 生成感。

### 5.4 通用 concierge MVP

- 不写代码，先用 AI + 人工帮 3 个用户完成一次“故事书/分享卡”。
- 记录：耗时、用户反馈、愿意付多少钱、是否会再次使用。
- 如果人工都做不好，产品化也做不好。

### 5.5 放弃/继续门槛

| 信号 | 判断 |
|---|---|
| 能拿到 ≥2 段真实方言录音 + 授权 | 继续 |
| 10 人里 ≥7 人完成 3 幕故事 | 继续 |
| ≥3 人主动说“想录家人声音” | 强信号 |
| ≥2 人愿意付 ≥39 元/本 | 强信号 |
| 用户觉得“和猫箱/星野没区别” | 换切口或强化真实素材 |
| 素材授权无法解决 | 放弃或换公有领域主题 |
| 8 天做不出完整闭环 | 砍地图/视频，只保留故事+分享卡 |
| 内容审核/隐私风险无法控制 | 放弃或改为纯公有领域内容 |

## 6. 推荐决策

### 6.1 用户决策记录（2026-11-15）

| 项目 | 决策 |
|---|---|
| 选定方向 | 非遗/方言互动叙事 → **声迹 · 方言故事书** |
| 目标赛事 | TRAE 好应用大赏赛（报名截止 2026-11-23） |
| 目标奖项 | 乐在其中奖、造物故事奖、值得一赏奖 |
| 关键约束 | 暂时没有可触达的 B 端真实用户 |
| 选择理由 | 可用家人/朋友录音独立启动；情绪价值强；演示与传播更适合比赛 |
| 已知风险 | 商业价值弱；已有“乡音计划·读侨批”等竞品；需用“家庭真实故事 + 互动 + 地图”做差异 |

**决策性质**：这不是“商业潜力最大”的选择，而是“当前资源约束下最可执行、最能在 8 天内做出真实作品”的选择。如果后续拿到软件外包/电商资源，A/B 仍可重新排期。

### 6.2 已选方案：C（声迹 · 方言故事书）

- 用自己/家人/朋友的方言录音，做 3 个种子故事（2 个公有领域 + 1 个真实家庭故事）。
- 核心体验：录音 → 转写/翻译/注释 → 3 幕互动 → 原声 + 字幕 → 分享卡 + 声音地图。
- 目标：用真实故事打“造物故事奖”，用互动/分享打“乐在其中奖”，用完整度打“值得一赏奖”。
- 详细执行见 `docs/contest/05-8天执行计划.md` 与 `已排期/03-非遗方言叙事/README.md`。

### 6.3 未选中但保留：A（交付验收官）

适合你未来拿到 B 端资源时再做：

- 你有 Node/Java/Spring 背景，做 Web 产品、文档解析、自动化检查都顺手；
- 你理解软件交付的痛，能讲出真实故事；
- 竞争空白明显，8 天能做出完整闭环；
- 即使不获奖，这个产品也可以继续服务自由职业者/外包公司，有商业价值。

### 6.4 未选中但保留：B（账单差异排查）

适合你未来能接触电商商家/财务/支付服务商时再做：

- 你能拿到脱敏账单样本；
- 你更擅长数据匹配、规则引擎、财务口径；
- ROI 清晰，演示数字冲击强。

### 6.5 如果你已有接近成熟的产品

优先提交已有产品，而不是从零造新项目。用第 3 节评分表评估它是否值得参赛；如果分数 ≥4，直接进入 `05-8天执行计划.md` 的“已有产品适配版”。
