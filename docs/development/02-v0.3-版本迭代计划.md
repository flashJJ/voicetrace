## 1. 版本定位

v0.2 解决了「评委能不能真的触发一次 AI」。v0.3 要解决的是「这个 AI 功能能不能被信任、能不能持续用」。

一句话：

> 从「能演示」到「能持续用」：让生成过程看得见、失败有兜底、质量有回归。

## 2. 目标与非目标

### 2.1 目标

1. 用户能看见生成在进行，而不是盯着一个静止按钮 15 秒。
2. 模型超时或失败时，页面仍然有可用内容，并明确说明发生了什么。
3. 每次生成的质量结果可以带走、可以对比。
4. 内容改动有自动校验，不靠人工记忆结构约束。
5. 故事从 9 个扩到 12 个，资料库从 91 条扩到 110 条。

### 2.2 非目标

- 不做多方言内容（数据结构已预留，内容留到 v1.0）
- 不做登录、家庭协作、云端故事册
- 不做实时语音识别
- 不引入新的 UI 框架或状态管理库
- 不为「看起来更 AI」增加无实际作用的模型调用

## 4. 关键方案

### 4.1 真流式生成进度

现状：后端已经是 NDJSON 流，但只在最后发送一次结果，中间只有心跳。用户看到的仍然是「生成中」。

v0.3 改为真正转发模型的流式输出：

```js
// 调用模型时加 stream: true
const upstream = await fetch(`${baseUrl}/chat/completions`, {
  method: "POST",
  body: JSON.stringify({ ..., stream: true }),
});

// 逐行解析 SSE，累计 content 长度
for await (const chunk of upstream.body) {
  const text = decoder.decode(chunk, { stream: true });
  // 解析 data: {...}，读取 choices[0].delta.content
  // 每累计 120 字或每 3 秒发送一次进度
  send({ type: "stage", stage: "generating", chars: total });
}
```

接口事件协议：

```json
{"type":"ping"}
{"type":"stage","stage":"preparing"}
{"type":"stage","stage":"generating","chars":320}
{"type":"stage","stage":"validating"}
{"type":"result","promptVersion":"v3-2026-12", "...": "..."}
{"type":"error","error":"...","hint":"..."}
```

兼容策略：旧前端只读取最后一行 `type: "result"`，新增的 `stage` 事件会被忽略，不会破坏现有版本。

前端展示：

- `preparing`：正在整理素材
- `generating`：已写 320 字
- `validating`：正在对照黄金样品验收

注意：JSON 在生成完成前不是合法结构，不能边生成边解析。进度只展示字数与阶段，最终仍一次性解析。

### 4.2 超时与失败降级

触发条件：模型超时、返回非 2xx、输出无法解析、输出被长度截断。

处理顺序：

1. 若该素材有黄金样品，返回黄金样品作为降级结果
2. 响应标记 `fallback: true` 与 `fallbackReason`
3. 前端显示明确提示：「本次生成超时，当前展示的是黄金样品」，并提供「重试一次」
4. 若没有黄金样品，返回结构化错误，并给出可操作建议

响应示例：

```json
{
  "type": "result",
  "fallback": true,
  "fallbackReason": "timeout",
  "mock": true,
  "model": "golden-sample",
  "output": {},
  "validation": []
}
```

关键原则：**降级必须被看见**。不能把黄金样品伪装成模型输出。

### 4.3 验收报告导出

v0.3 先做成本最低的 Markdown 复制：

```markdown
# 声迹 · 生成验收报告

- 素材：月光光（yue-rhyme-moonlight）
- 模式：正经
- 模型：deepseek-v4.1-flash
- Prompt：v3-2026-12
- 耗时：13.2s
- 验收：7 / 7 通过
- 状态：真实生成

| 检查项 | 结果 |
|---|---|
| json_schema_valid | 通过 |
| scene_count == 3 | 通过 |
```

前端提供「复制报告」按钮，成功后按钮短暂变为「已复制」。不新增后端接口。

Canvas 图片版放 P2，复用 `ShareCard.jsx` 的绘制工具。

### 4.4 Prompt 版本化

把提示词从路由中抽出：

```text
web/lib/prompt.js
  ├─ PROMPT_VERSION = "v3-2026-12"
  ├─ SYSTEM_PROMPT
  └─ buildPrompt(item, mode)
```

接口响应与验收报告都带上 `promptVersion`，用于对比不同版本的输出差异。

同时把 `validate` 抽到 `web/lib/validate-story.js`，让路由只负责编排。

### 4.5 内容校验脚本

新增 `web/scripts/validate-content.mjs`，在 CI 与本地构建前执行。

检查项：

| 对象 | 规则 |
|---|---|
| 故事 | 5 幕、6 个选择、4 个唯一目标、2 个结局、0 个悬空 `next` |
| 故事 | `slug` 唯一、`mode` 合法、封面文件存在 |
| 素材 | `id` 唯一、`modes` 合法、`source` 非空、`type` 合法 |
| 黄金样品 | `storyId` 能在素材中找到、`mode` 合法、`glossary.term` 不重复 |

输出格式：每条错误一行，包含文件名与字段；有错误时退出码非 0。

CI 改动：

```yaml
- run: node scripts/validate-content.mjs
- run: node scripts/build-static.mjs
```

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型流式返回的 JSON 不完整 | 无法解析 | 只在流结束后解析；失败时走降级 |
| 平台网关对长流式连接有限制 | 进度中断 | 保留非流式回退开关 `LLM_STREAM=false` |
| 真实录音拿不到 | P1 延期 | 不阻塞发布，保留 TTS 作为默认 |
| 新增故事语言质量不足 | 可信度下降 | 每个故事至少一次母语通读，不确定内容标「相传」 |
| 内容校验脚本误报 | CI 阻塞 | 脚本先在本地跑通，再接入 CI |
| 改动影响比赛线上版本 | 评审风险 | 比赛期间冻结 `main`，所有改动在 `release/v0.3` |

## 8. 发布与回滚

发布步骤：

1. `release/v0.3` 完成验收清单
2. 合并到 `main`，触发 GitHub Pages 静态构建
3. 部署 Trae 服务端版本，注入运行时环境变量
4. 观察 24 小时：生成成功率、429、504、错误日志
5. 无异常后更新 `README.md` 变更记录，打 tag `v0.3.0`

回滚策略：

- 代码回滚到 tag `v0.2.0`
- 服务端在 Trae 回滚到上一个成功部署
- 静态站由 GitHub Actions 重新部署上一提交
- 数据文件（故事、素材）向前兼容，回滚不需要迁移

## 9. 发布后

v0.3 完成后，进入 v1.0 的立项评估。v1.0 的前置条件：

- 有稳定的真实录音素材（至少 5 段）
- 有母语者可参与校对
- 模型成本可预测
- 限流方案能覆盖多实例

未满足前，不启动多方言内容。
