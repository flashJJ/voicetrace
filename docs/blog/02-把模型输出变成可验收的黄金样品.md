# 把模型输出变成可验收的黄金样品

> 项目：声迹 · VoiceTrace\
> 关键词：LLM 评测、结构化输出、事实约束、黄金样品

## 问题：生成式输出没有唯一答案

做一个「素材 → 三幕故事」的 AI 功能，最难的不是调通接口，而是回答一个问题：

> 生成出来的东西，凭什么算合格？

传统断言式测试在这里基本失效。同一段童谣，模型可以写成温情版、悬疑版、说书版，都不算错。但如果它把「西关」写成「东山」，把「趟栊门」解释成「木窗」，那就是错。

声迹的解法是：**为每条素材准备一份黄金样品，再用结构化的规则去对照。**

## 黄金样品是什么

黄金样品不是「标准答案」，而是「参考答案 + 必查项」：

```json
{
  "id": "golden-moonlight-v1",
  "storyId": "yue-rhyme-moonlight",
  "mode": "heritage",
  "input": { "title": "月光光", "text": "月光光，照地堂……" },
  "expected": {
    "language": "yue",
    "entities": ["月光", "地堂", "虾仔", "阿妈", "阿爷", "牛", "秧"],
    "glossary": [
      { "term": "地堂", "meaning": "天井、屋前空地" },
      { "term": "虾仔", "meaning": "对小孩的昵称" },
      { "term": "睇牛", "meaning": "放牛" }
    ],
    "scenes": [
      { "act": 1, "title": "骑楼下的月光", "summary": "……", "choices": ["乖乖睡觉", "问阿妈插秧是什么"] }
    ],
    "endings": ["虾仔在月光下睡着，梦里有一片插秧的水田。"],
    "translationZh": "月光照亮天井……",
    "safetyFlags": []
  }
}
```

`expected.entities` 和 `expected.glossary` 是最关键的部分：它们把「不许编造」变成了可执行检查。

## 7 项检查

真实模型返回后，接口不会直接展示内容，而是先跑 7 项检查：

```js
push("json_schema_valid", Boolean(output && output.scenes && output.glossary && output.translationZh));
push("scene_count == 3", output.scenes.length === 3);
push("ending_scene_present", output.scenes[2].choices.length === 0);
push(
  "glossary_terms_present",
  golden.expected.glossary.every((expected) =>
    output.glossary.some((actual) => actual.term === expected.term)
  )
);
push("translation_present", Boolean(output.translationZh));
push(
  "entities_are_grounded",
  output.entities.every(
    (entity) => sourceText.includes(entity) || golden.expected.entities.includes(entity)
  )
);
push("choices_present", output.scenes.slice(0, 2).every((scene) => scene.choices.length >= 2));
```

每一项都对应一个真实的失败模式：

| 检查 | 拦截的问题 |
|---|---|
| `json_schema_valid` | 模型返回 Markdown、解释文字或残缺 JSON |
| `scene_count == 3` | 只写了 2 幕或擅自加到 4 幕 |
| `ending_scene_present` | 结局幕还在给选项，读者永远读不完 |
| `glossary_terms_present` | 把「地堂」改写成「天井地堂」等组合词 |
| `translation_present` | 只有粤语，不懂粤语的人被挡在门外 |
| `entities_are_grounded` | 编造素材里没有的人物、地名、年份 |
| `choices_present` | 前两幕没有分支，退化成线性文本 |

`glossary_terms_present` 用严格相等，是因为模型很喜欢「优化」词条：把「睇牛」写成「看牛」、把「虾仔」写成「小虾仔」。这类改写看起来更通顺，但会让方言词失去原貌。

## Prompt 里的约束怎么落地

验收规则如果只写在代码里，模型每次都会犯同样的错。所以约束要同时写进 Prompt：

```text
实体规则：
- entities 只能从上面的素材原文/摘要中逐字出现的名词里选。
- 不要输出同义词、解释性短语、组合词或扩展地名。
- 每个 entity 必须能在素材原文/摘要中找到完全相同的字。

必须覆盖的方言词（term 必须与这些词完全一致）：
地堂、虾仔、睇牛
```

「逐字出现」这个说法比「不要编造」更有效。前者是可执行的字符串比较，后者只是态度。

## Mock 模式：没有 Key 也能跑通流程

开发和演示时经常没有模型额度。接口在缺少 Key 时不会报错，而是把黄金样品当作 Mock 输出：

```js
return Response.json({
  mock: true,
  model: "mock-golden-sample",
  output: golden.expected,
  validation: validate(golden.expected, golden, sourceText),
  note: "未配置 LLM_API_KEY，当前返回黄金样品作为 Mock 输出。",
});
```

这样前端、验收逻辑、演示流程都能在没有 Key 的环境里完整走一遍。UI 上会明确区分「Mock 模式」与「真实模型」，不混淆展示。

## 自动检查查不到的东西

7 项检查能拦住结构错误和事实幻觉，但拦不住：

- 故事是否好看
- 方言是否地道
- 鬼故事是否越界成了低俗
- 翻译是否自然

这些只能靠人读。黄金样品的定位是「第一道闸门」，不是「质量认证」。

所以项目里仍然保留了人工通读环节，尤其是鬼故事和野史——这两类最容易被模型写成猎奇或造谣。

## 一点经验

如果你的 AI 功能输出是结构化的，先别急着做评分模型。准备 5-10 份人工确认过的样品，把「必须出现」「不许出现」「必须几段」写成代码，往往比一个模糊的「请打分」更可靠。

能自动化的先自动化，剩下的明确交给人。这比假装全自动诚实，也更容易维护。
