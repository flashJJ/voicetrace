# 13 秒网关超时下的流式生成

> 项目：声迹 · VoiceTrace\
> 关键词：LLM 接口、网关超时、NDJSON、流式响应、推理模型

## 现象：本地好的，线上 504

AI 工坊部署到云端后，第一版接口在本地测试完全正常，线上却稳定失败：

```text
status=504
elapsed=30414ms
```

平台日志给出了更直接的证据：

```text
[FaaS System] request canceled, request: POST /api/generate-story,
time elapsed: 17.972968155s
```

模型还没写完，网关已经判定请求超时。普通 JSON 响应必须等模型全部生成完才能返回，而一次完整的 3 幕故事生成需要 10-20 秒，正好卡在网关的容忍边界之外。

## 第一个坑：推理模型把 token 全花在思考上

排查时先单独测了模型。构造一个相近的 Prompt，`max_tokens: 1400`：

```text
elapsed=17567ms finish=length contentLen=0 completion=1400
```

`finish=length`、`contentLen=0`：1400 个输出 token 全部用在思考上，正文一个字都没有，还耗掉了 17.5 秒。

这说明用的是推理模型（`deepseek-v4.1-flash`），默认会先思考。对故事生成这种结构化任务，思考不是必需的，反而把时间和 token 都吃掉了。

火山方舟的接口支持关闭：

```js
const disableThinking = process.env.LLM_DISABLE_THINKING
  ? process.env.LLM_DISABLE_THINKING === "true"
  : baseUrl.includes("volces.com");

body: JSON.stringify({
  model,
  max_tokens: 1500,
  ...(disableThinking ? { thinking: { type: "disabled" } } : {}),
  response_format: { type: "json_object" },
  messages: [...]
})
```

关闭后同一个 Prompt：

```text
elapsed=9517ms finish=stop contentLen=1164 completion=695
```

9.5 秒、正文 1164 字符、正常结束。问题解决了一半。

## 第二个坑：网关不等

9.5 秒是短 Prompt 的成绩。真实接口要带完整素材、模式说明和格式约束，耗时回到 12-19 秒，仍然可能触发网关超时。

换更快的模型是一个办法，但会牺牲中文表达能力。更通用的办法是**让响应在生成期间持续有数据**。

HTTP 没有规定响应必须一次返回。只要服务端持续写 chunk，网关看到的就是一个「活跃」的连接，不会按首字节或总时长判超时。

于是接口从「一次性 JSON」改成 NDJSON：

```js
function streamResult(work) {
  const encoder = new TextEncoder();

  const stream = new ReadableStream({
    async start(controller) {
      const send = (payload) =>
        controller.enqueue(encoder.encode(`${JSON.stringify(payload)}\n`));

      const timer = setInterval(() => send({ type: "ping" }), 4000);

      try {
        const payload = await work();
        send({ type: "result", ...payload });
      } catch (error) {
        send({ type: "error", error: error.message });
      } finally {
        clearInterval(timer);
        controller.close();
      }
    },
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/plain; charset=utf-8",
      "Cache-Control": "no-store, no-transform",
      "X-Generation-Stream": "ndjson",
    },
  });
}
```

几个细节：

- **每 4 秒一个心跳**，小于网关常见的 5-10 秒空闲超时
- **`no-transform`**，避免中间层压缩或缓冲把心跳攒起来
- **自定义响应头** `X-Generation-Stream`，前端据此判断走流式还是普通 JSON
- 用 `text/plain` 而不是 `application/json`，避免某些网关尝试解析不完整的 JSON

## 前端怎么读

前端不能再用 `response.json()`，要读 `ReadableStream` 并按行解析：

```js
const response = await fetch("/api/generate-story", { method: "POST", body });

if (response.headers.get("x-generation-stream") === "ndjson" && response.body) {
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  let payload = null;

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop() || "";
    for (const line of lines) {
      if (!line.trim()) continue;
      const message = JSON.parse(line);
      if (message.type === "result") payload = message;
      if (message.type === "error") throw new Error(message.error);
    }
  }

  if (!payload) throw new Error("生成没有返回结果，请重试一次");
}
```

`buffer = lines.pop()` 是必须的：一次 `read()` 可能只拿到半行，直接解析会抛错。

## 结果

同一套接口，三种输入实测：

| 输入 | 耗时 | 结果 |
|---|---|---|
| 资料库素材《月光光》 | 13.2 秒 | 200，3 幕，7/7 通过 |
| 自定义粤语素材 + 鬼故事模式 | 9.0 秒 | 200，3 幕，7/7 通过 |
| 另一条自定义素材 | 18.8 秒 | 200，3 幕，7/7 通过 |

18.8 秒那次如果没有心跳，大概率又是一次 504。

## 还需要哪些保护

流式只解决「连接被判超时」，不解决「模型挂了」和「成本失控」。所以接口同时保留：

- `AbortSignal.timeout(15000)`，应用先于网关放弃，返回可读的错误
- `finish_reason === "length"` 时明确报「输出被截断」，而不是抛一个 JSON 解析错误
- 错误也走 `type: "error"` 事件，前端有统一的失败分支

## 小结

把大模型接进真实 Web 应用，失败往往不在模型，而在模型与用户之间的那几层基础设施：

- 推理模型的默认行为可能完全不适用
- 网关的超时阈值通常比应用短
- 一个看似正常的 504，背后可能是「响应没有及时开始」

先量出真实耗时，再决定是优化 Prompt、换模型，还是改传输方式。流式不是炫技，是在受限环境下让功能可用的必要手段。
