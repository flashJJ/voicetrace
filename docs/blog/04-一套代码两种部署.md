# 一套代码，两种部署：静态站与实时生成怎么共存

> 项目：声迹 · VoiceTrace\
> 关键词：Next.js 静态导出、standalone、GitHub Pages、双形态

## 为什么要两种部署

同一个产品，有两类需求：

- 评委、路人打开链接，应该**立刻看到内容**，不能等服务器、不能白屏
- 想验证 AI 的人，应该能**真的触发一次生成**，而不是看录屏

GitHub Pages 免费、稳定、国内可访问，但只能托管静态文件。实时生成必须有 Node 进程。

结论不是二选一，而是让一套代码产出两种形态。

## 用环境变量切换输出模式

Next.js 的 `output` 只能取一个值，所以用构建时变量切换：

```js
const isStatic = process.env.STATIC_EXPORT === "true";

const nextConfig = {
  env: {
    NEXT_PUBLIC_BASE_PATH: isStatic ? "/voicetrace" : "",
    NEXT_PUBLIC_SITE_URL: isStatic
      ? "https://flashjj.github.io"
      : "http://localhost:3000",
  },
  ...(isStatic
    ? {
        output: "export",
        trailingSlash: true,
        basePath: "/voicetrace",
        assetPrefix: "/voicetrace/",
      }
    : { output: "standalone" }),
};
```

静态站部署在 `https://flashjj.github.io/voicetrace/`，所有资源路径都要带 `/voicetrace` 前缀。服务端形态部署在根路径，前缀为空。

## 第一个连锁问题：所有静态资源路径

写死 `/covers/moonlight.webp` 的代码，在 GitHub Pages 上会变成 404，因为真实路径是 `/voicetrace/covers/moonlight.webp`。

解决办法是把路径拼接收口到一个模块：

```js
const basePath = process.env.NEXT_PUBLIC_BASE_PATH || "";

export const cover = (name) => `${basePath}/covers/${name}.webp`;
export const heroImage = cover("hero");
export const whyImage = cover("why");
```

规则很简单：**任何 public 资源都不要手写绝对路径**。

## 第二个问题：静态导出不支持 API 路由

`app/api/generate-story/route.js` 是动态路由。只要它存在，`output: "export"` 就会报错。

静态构建脚本的做法是：构建前把 `app/api` 临时移走，构建后还原。

```js
fs.renameSync("app/api", ".api-backup");

try {
  execSync("npx next build", {
    stdio: "inherit",
    env: { ...process.env, STATIC_EXPORT: "true" },
  });
} finally {
  fs.renameSync(".api-backup", "app/api");
}
```

这样仓库里始终保留 API，静态产物里没有它，本地开发也不受影响。

## 第三个问题：standalone 不是完整包

`output: "standalone"` 只包含服务端代码和依赖追踪结果，**不会自动带上 `.next/static` 和 `public`**。

直接 `node .next/standalone/server.js` 会看到没有样式的页面。

部署脚本必须补齐：

```sh
cp -R .next/standalone/. dist/
mkdir -p dist/.next
cp -R .next/static dist/.next/static
cp -R public dist/public
```

同理，`run.sh` 也要复制进产物目录，因为部署平台以 `dist` 作为运行根。

## 第四个问题：前端要知道自己在哪

静态站不能调用 `/api/generate-story`。如果不管，用户点了生成会看到一个 404 或一串报错。

项目用 `NEXT_PUBLIC_BASE_PATH` 判断当前形态：

```js
export const LIVE_STUDIO_URL = "https://<服务端域名>/studio";
export const isStaticExport = Boolean(process.env.NEXT_PUBLIC_BASE_PATH);
```

在静态站上：

- 导航里的「AI 工坊」直接外链到服务端版本
- `/studio` 页面顶部出现说明条和跳转按钮
- 即使点了生成按钮，也会自动打开在线版本，而不是报错

这比「让用户自己猜为什么不能生成」体验好得多。

## 元数据也要跟着换

`layout.js` 的 OG 图需要绝对地址。`metadataBase` 用 `NEXT_PUBLIC_SITE_URL`，静态站指向 GitHub Pages，服务端版指向自己的域名。

```js
export const metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_SITE_URL || "http://localhost:3000"),
  openGraph: { images: [`${basePath}/og.jpg`] },
};
```

否则分享出去的卡片会指向 `localhost:3000`，谁也打不开。

## 几个容易忽略的坑

### robots.txt 必须声明静态

静态导出时，`app/robots.js` 需要：

```js
export const dynamic = "force-static";
```

否则构建直接失败。

### 图片的 height 属性会压制 aspect-ratio

```html
<img width="900" height="505" />
```

这会让 CSS 的 `aspect-ratio` 失效。移动端改比例时必须同时写 `height: auto`。

### 静态站的 /studio/ 会 308

带尾斜杠的路径会被重定向到无斜杠版本。写链接和测试时要注意，不要把 308 当成故障。

## CI 与手动部署的分工

GitHub Actions 只做静态站：

```yaml
- run: npm ci
- run: node scripts/build-static.mjs
- uses: actions/upload-pages-artifact@v3
  with:
    path: web/out
```

服务端版本走手动部署，因为要注入模型 Key、配置限额、检查运行时日志。这些不适合写进公开仓库的 CI。

## 小结

一套代码两种形态，核心不是 Next.js 的配置技巧，而是把「形态差异」集中到少数几个地方：

- 构建配置：`next.config.mjs`
- 资源路径：`lib/image.js`
- 运行时判断：`lib/live.js`
- 构建脚本：`scripts/build-static.mjs`

其余业务代码不需要知道自己在哪种形态里运行。这样两边的功能不会越走越远。
